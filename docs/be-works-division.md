# 1. 나누는 원칙

1. **전체 분량과 시기별 일감을 1 : 1 : 1로 맞춘다.** 초반(기반)에 바쁜 영역과 중후반(코어 · AI · 시간표)에 바쁜 영역을 짝지어, 프로젝트 끝까지 세 사람 중 누구도 비거나 밀리지 않게 한다.
   - **BE 1:** 초반 **계정 · 보안 · 암호화 · 메일** → 중후반 **AI 해석 중계 · 되묻기 · 대화 기록 · 캡처 인식**
   - **BE 2:** 초반 **아이템 기본 · 오프라인 동기화 · 묶음 쓰기 틀** → 중후반 **상세 패치 · 연결 · 할 일/노트 · 충돌 · 되돌리기 · 정리 대기**
   - **BE 3:** 초반 **입력 화면 시드 · 컬렉션 · 반복 기본** → 중후반 **반복 나누기 · 미루기 · 휴지통 · 설정 · 시간표 · ICS**
2. **공통 파일만 맨 처음에 확정해 `main`에 올리고, 나머지는 각자 알아서 만든다.** 세 사람이 AI 도구로 동시에 작업할 때 같은 파일을 건드려 Git 충돌이 나지 않도록, 전체 DB 스키마 · 공통 응답/에러 틀 · 서버 설정 · 내부 인터페이스만 맨 처음에 함께 확정하고 시작한다(2.2절).
3. **한 패키지와 한 테이블의 쓰기는 한 사람만 맡는다.** 공통 파일을 올린 뒤로는 각자 맡은 폴더(패키지) 안에서 API와 로직을 알아서 만들고, 다른 담당의 기능이 필요하면 미리 정의해 둔 내부 인터페이스만 부른다(2.3절).
4. **같은 성격의 규칙은 한 사람에게 모은다.** 아이템 본체의 칸 단위 병합 · 충돌 · 되돌리기 이력은 **BE 2**가 한 줄기로 맡고, iCalendar 기반의 반복 · 회차 예외 · 마스터 나누기 · 시간표 겹침 · ICS는 **BE 3**이 한 줄기로 맡는다.

## 2.2 코딩 전에 먼저 확정해 올리는 공통 파일 5가지

기능 구현 브랜치를 나누기 전에 세 사람이 아래 다섯 가지를 먼저 확정해 `main`에 올린다. 세부 스키마와 코드는 「BE 공통 파일 명세」를 따른다.

| 순서 | 공통 파일                                                                   | 내용                                                                                                                                                                                                                                                                                                                                                                                        |
| ---- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | **DB 스키마와 엔티티 (`V1__init_schema.sql`)**                              | 명세 `F-12`의 모든 테이블과 컬럼을 Flyway 초기 마이그레이션(`V1__init_schema.sql`) 하나로 정의하고 JPA `ddl-auto: validate`로 검증한다. 개발 중 스키마 변경이 필요하면 기존 파일을 고치지 않고 담당 테이블의 번호 대역(`V1xx` BE 1 · `V2xx` BE 2 · `V3xx` BE 3, `out-of-order: true`)으로 새 마이그레이션 파일만 추가한다                                                                   |
| 2    | **공통 응답 틀과 담당별 에러 코드 틀**                                      | 공통 응답 꼴과 예외 처리기 틀을 잡아 두고, 에러 코드 파일은 각자 개발하며 자유롭게 추가해도 충돌하지 않도록 `BE 1` · `BE 2` · `BE 3` 파일로 나눠 둔다                                                                                                                                                                                                                                       |
| 3    | **서버 설정 · 로깅 · 공통 필터 (`application.yml` · `logback-spring.xml`)** | DB · Flyway · JPA(`ddl-auto: validate`) · Redis · 세션 · 쿠키/CORS(`4.3`) · 호스트 Nginx 포워딩 헤더 인식 · 메일(SMTP) · KMS · 외부 AI 설정 키 이름과 엔드포인트별(`GET` · `POST` 등) IP · 상태 로깅 필터(`EndpointAccessLogFilter`, 명세 `4.3` 민감값 제외), 20MB 단위 `.gz` 압축 롤링 보관 설정(`logback-spring.xml`)을 먼저 넣어 둔다                                                    |
| 4    | **담당 간 내부 인터페이스**                                                 | 다른 담당의 기능을 부를 때 쓸 인터페이스 껍데기(아래 2.3절)와 임시 동작(Mock)을 먼저 넣어 두어, 상대 구현이 끝나기 전에도 독립해서 개발한다                                                                                                                                                                                                                                                 |
| 5    | **배포 · Docker 정형화 파일**                                               | `Dockerfile`(x86_64 멀티스테이지 · ProGuard 바이트코드 난독화 · 평문 소스 제거), `proguard.pro`, `docker-compose-deployment.yaml`(`eagleindesert/<디렉토리 이름>` 이미지 풀 · 호스트 Nginx 포워딩 포트), `.env.example`, 프로젝트 루트의 `start.sh`(버전 인자 `pull` 및 `up -d`, 일반 `docker compose` CLI 호환), `/scripts/build-push.sh`(buildx 부팅 시 자동 재시작 방지)를 함께 고정한다 |

## 2.3 담당 사이에 부르는 내부 인터페이스

남의 폴더 안 코드는 직접 고치지 않고 아래 인터페이스로만 부른다.

| 인터페이스                        | 제공하는 쪽     | 부르는 쪽       | 언제 쓰나                                                                                                                                                                                         |
| --------------------------------- | --------------- | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **사용자 글 암복호화**            | **BE 1**        | **BE 2 · BE 3** | 아이템 이름 · 본문 · 장소 · 태그, 컬렉션 이름, 가져온 ICS 값, 지침, 이력, 충돌 기록, 대화 기록을 사용자별 데이터 키로 암호화 · 복호화할 때(`4.4`)                                                 |
| **아이템 단건 · 묶음 쓰기**       | **BE 2**        | **BE 1 · BE 3** | AI 확정 결과(`F-43` · `F-47`), 할 일 미루기(`F-18`), 시간표 만들기(`F-31`), ICS 가져오기(`F-42`), 일괄 삭제와 휴지통(`F-15` · `F-38` · `F-40`)에서 아이템을 한 묶음으로 만들거나 고치거나 지울 때 |
| **충돌 후보 등록**                | **BE 2**        | **BE 3**        | 반복 마스터 변경(`F-24`)이나 ICS 재가져오기(`F-42`)로 짝이 없거나 다른 회차와 겹치는 예외 회차를 풀지 않은 충돌(`F-45`)로 남길 때                                                                 |
| **반복 · 시간표 묶음 연산**       | **BE 3**        | **BE 2**        | 묶음 쓰기(`F-43`)나 동기화(`F-44`) 안에서 회차 예외(`F-23`), 반복 나누기(`F-24` · `F-33`), 시간표 겹침 검사(`F-30`)를 실행할 때                                                                   |
| **계정 · 워크스페이스 수명 연동** | **BE 2 · BE 3** | **BE 1**        | 가입할 때 기본 컬렉션을 만들고(`F-01` → `F-40`), 탈퇴 30일 뒤 그 계정의 아이템 · 단독 컬렉션 · 설정을 물리 삭제할 때(`F-06` → `F-15` · `F-40`)                                                    |

# 6. 정할 것

FE/BE 기능 분배안 5장의 결정 항목을 아래 담당이 맡는다.

- **공통 테스트 사례 (`BE 2` · `BE 3`):** iOS와 웹이 같은 답을 내야 하는 규칙 가운데 **합치기 · 빈 시간 · 조회**는 **BE 2**가, **회차 계산 · 반복 예외 · 시간표 겹침 · ICS**는 **BE 3**이 입력과 기대 결과 표를 관리한다.
- **"내가 아니다" 확인 화면 (`BE 1`):** 로그인 없이 여는 웹 화면(`F-05`)이다. 웹이 iOS보다 늦게 시작하면 **BE 1**이 서버의 단순한 확인 페이지로 먼저 낸다.
- **외부 AI와 캡처 인식 엔진 (`BE 1`):** 문장 해석(`F-43`)과 시간표 캡처 인식(`F-34`)에 무엇을 쓸지, 응답 시간 상한과 사용자별 한도 값을 **BE 1**이 정한다.
- **옛 API 문서 확인 (`BE 1` · `BE 2` · `BE 3`):** 옛 `개발용 API Schema (REST · v2.0)`에서 각자 맡은 영역에 참고할 요청 · 응답 꼴이 있는지 각자 개발하면서 확인한다.
